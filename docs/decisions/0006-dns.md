# 0006: DNS for the homelab zone

**Status:** accepted · 2026-11

## Decision

- The UniFi gateway stays the DNS resolver for all clients.
- A UniFi Forward Domain rule sends `home.znd4.dev` to a floating IP (VIP).
- One or more NixOS hosts run CoreDNS as the authoritative server for the zone.
- keepalived (VRRP) moves the VIP to a healthy DNS host.

The module is `homelab.services.dns` in `nix/modules/services/dns.nix`.

## Why the gateway stays the resolver

Every NixOS host uses remote disk unlock (decision 0002). After a power
outage, each host waits for its passphrase. If the homelab resolved all DNS,
the full house would have no DNS until someone unlocked a host.

With the forward, a homelab outage stops only `*.home.znd4.dev`. Internet
DNS continues to work.

## Records come from the flake

CoreDNS answers only for `home.znd4.dev`. It refuses all other queries, so it
is not an open resolver.

The zone file comes from the flake, at build time:

- One A record for each host, from `homelab.lanAddress`.
- One A record for each vhost in `homelab.reverseProxy.vhosts`. It points at
  the host that serves the vhost.
- The records in `homelab.services.dns.extraRecords`.
- `version.home.znd4.dev`: a TXT record with the git revision of the flake.

The build fails if two records have the same name.

## No consensus

Each DNS host builds the full zone from the same commit. The hosts do not
send data to each other at run time. So they need no consensus algorithm.

Consensus is necessary only if something writes records at run time, for
example external-dns in Kubernetes. Then CoreDNS would need a shared store,
such as etcd. The homelab does not need that now.

## Deploys are not simultaneous

A deploy changes one host at a time. During a deploy, two DNS hosts can give
different answers. A failed deploy can leave a difference for a longer time.

This is acceptable for these reasons:

- The record TTL is 60 seconds. Client caches already show old answers for that
  long.
- Clients send queries to the VIP. Only one host holds the VIP, so clients see
  one host at a time.
- Most changes add a record. An added record that is present on one host first
  causes no problem.

## Rolling deploy

A bad config can stop CoreDNS. A deploy to all hosts at once would then stop
DNS everywhere. Deploy in this order:

1. Deploy one host that does not hold the VIP.
2. Check it: `dig TXT version.home.znd4.dev @<host lanAddress>`.
3. Deploy the other followers in the same way.
4. Deploy the host that holds the VIP last.

Two checks stop a bad deploy:

- The CoreDNS unit has an `ExecStartPost` check. It queries
  `version.home.znd4.dev` on 127.0.0.1. The answer must be the git revision of
  the new build. If that answer does not come in about 30 seconds, the unit
  fails and the switch fails.
- The check compares the exact answer. When `dig` cannot reach a server, it
  writes the error text to stdout. A check for "any output" thus always passes.
- deploy-rs "magic rollback" restores the previous system if deploy-rs
  cannot reach the host over SSH after the activation.

## Detect skew

Each host serves its own `version.home.znd4.dev`. Compare the hosts:

```sh
for h in <lanAddress of each DNS host>; do dig +short TXT version.home.znd4.dev @$h; done
```

Different answers for more than a few minutes mean that a deploy failed.
Monitoring can alert on this later.

## VRRP

- keepalived runs the same query as a health check. A host that runs but does
  not answer gives up the VIP.
- VRRP uses unicast to the other DNS hosts. UniFi IGMP snooping can drop
  VRRP multicast.
- The healthy host with the highest `priority` holds the VIP.
- CoreDNS binds the VIP on every DNS host (`net.ipv4.ip_nonlocal_bind`). It
  needs no restart when the VIP moves.

## Later

- k8s-gateway in the Talos cluster can answer for services that run in
  Kubernetes. The forward then goes to the cluster, or the NixOS hosts
  forward a subzone to it.
- Not verified: whether a UniFi Forward Domain rule accepts more than one
  target. The VIP makes this unimportant.

## Test

`nix build .#checks.x86_64-linux.dns-vm` starts two DNS hosts and a client in
VMs. The test checks the records, NXDOMAIN, the refusal of other zones, VIP
failover in both directions, and the Caddy proxy to CUPS. CI runs it on each
push.
